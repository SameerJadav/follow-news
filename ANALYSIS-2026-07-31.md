## 3. Critical and high findings

### F1 — Follow #3 is permanently frozen and lies about it · **Critical**

`followed/3/dossier.json` reports `research_state: "complete"`, `rounds: 10`,
`calls: 54`, and **631 open questions**. `docs/follow-3.html` renders "The full
picture" — the finished state. A reader sees a fully-researched, current story.

It is neither. The follow is out of lifetime budget and cannot make another
call. Computed live during this analysis:

```
write_reserve(ledger of 154)          = 7        # max(3, ceil(154/30)+1)
_afford: calls + reserve < MAX_CALLS   = 54 + 7 = 61 < 60  ->  False
```

So `research()` immediately takes the `call_ceiling` branch, sets
`research_state = "capped"`, and returns `"capped"`. Then `_update_follow`
overwrites it:

- `follow.py:567` — `dossier.research(...)` returns `"capped"`; **the return
  value is discarded**.
- `follow.py:571` — ledger unchanged, so this reads as a quiet day.
- `follow.py:573` — `dsr["research_state"] = "complete"`.

The `capped` verdict is written to disk by `research()` and then overwritten in
the same call stack. This is directly contrary to two stated invariants in
`CLAUDE.md`: *"A `capped` dossier reports itself as capped"* and *"No silent
caps."*

**This is not a prediction — it already happened three times on 2026-07-31.**
All three runs in `debug/2026-07-31/trace.jsonl` are identical:

```
follow: sweep -> 0 researching, 1 due; budget grounded=18 schema=14
dossier: #3 CAPPED at 54 call(s); 631 question(s) left in the frontier
follow: #3 -> quiet, no new ledger entries
follow: run -> done, 0 grounded call(s) this run
```

`rounds` and `calls` have been frozen at 10/54 across `b5f4b29`, `ecda271` and
`dbfd2ce`. Grounded budget sat at 18/18 unused. The dossier's own `capped`
event *is* in `trace.jsonl` — the tracer is fine; the state written to
`dossier.json` and rendered to the page is the part that is wrong.

> Evidence: `followed/3/dossier.json`; `debug/2026-07-31/trace.jsonl`;
> `follow.py:551-581`; `dossier.py:1496-1516`; `docs/follow-3.html`.

**Fix:** honour the return value of `dossier.research()` in `_update_follow` —
if it is `"capped"`, keep `capped` and do not treat an empty delta as "quiet".

### F2 — The gap detector makes saturation mathematically unreachable · **High**

This is the root cause of F1 and the reason 54 calls bought so little.

`followed/3/dossier.json` has `span: {start: "2015-05-01", end: "2026-07-28"}` —
**4,106 days = 587 weekly buckets**, of which only **32 contain any entry**.

`gap_questions()` (`dossier.py`) buckets the ledger by week and raises a
question for every bucket at or below `median × GAP_DENSITY_RATIO`. With 154
entries over 587 buckets the median is 0, so the function falls back to
`max(1, 154 // 587)` = 1, giving `floor = 0.34`. Every empty week clears it.

Measured live in this analysis:

```
gap_questions(ledger, span)      -> 547 questions
entity_asymmetry_questions(...)  -> 0
saturated(dsr)                   -> False
```

`saturated()` returns False unless `gap_questions()` is **empty**. To empty it,
the dossier would need an entry in essentially all 587 weeks of an 11-year
span. **The loop-until-dry exit is dead code for any long-span story.** The
research loop can therefore only ever end on `MAX_ROUNDS`, the daily budget, or
the lifetime ceiling — which is exactly what happened.

The frontier composition confirms where the calls went. Of 631 open questions:

| origin | count |
|---|---|
| `gap` | **616** |
| `dangling` | 13 |
| `model` | 2 |

97.6% of the frontier is "What happened in this story between
`<week>` and `<week>`? The record is nearly empty for that period." for weeks
in 2015–2019. `pop_round` sorts by score, and gap questions score 0.75 —
below only the 0.95 delta question. So each round spent 1 call on "what
happened since yesterday" and the rest on decade-old empty weeks.

The yield curve shows the cost directly:

| round | day | entries gained | calls spent |
|---|---|---|---|
| 1 | 07-27 | +57 | 11 |
| 2 | 07-27 | +0 | 18 |
| 6 | 07-29 | +42 | 31 |
| 7 | 07-29 | +22 | 34 |
| 8 | 07-29 | +11 | 38 |
| 9 | 07-29 | +14 | 48 |
| 10 | 07-30 | +8 | 53 |

Rounds 6-10 spent 22 calls for 97 entries while the frontier stayed pinned
above 600. At ~9 questions drained per round it would take ~70 more rounds to
empty — against a lifetime ceiling that was already 6 calls away.

> Evidence: `followed/3/dossier.json` (`span`, `questions.open`);
> `dossier.py` `gap_questions`/`saturated`/`pop_round`; round lines in
> `debug/2026-07-{27,29,30}/trace.jsonl`.

**Fix options:** cap the number of gap questions admitted per round; bound the
gap detector to the story's *dense* era rather than the full span; or exclude
`gap` emptiness from the `saturated()` test. The span itself is defensible —
the 2015 entries are the Vyapam-era precedent — so bounding the detector is
better than truncating the span.

### F3 — `r.jina.ai` now 403s the project's User-Agent · **High, one-line fix**

On 2026-07-31 the digest escalated 13 articles to the Jina reader proxy and
**every one returned 0 characters**:

```
total rows 45 | jina_fired 13 | jina yielded>0 chars: 0
```

9 articles ended with 0 characters of text (4 × NDTV, 5 × France 24, all
HTTP 403 at origin); 4 more came back under the 600-char floor. That is
**13 of 45 articles (29%) with no usable body**. 2026-07-30 shows the same
shape (11 fired, 11 weak, 6 failed). 2026-07-27/28/29 were fine — Jina won
13, 3 and 4 extractions respectively. **The regression started around 07-30.**

`CLAUDE.md` states Jina escalation is what makes NDTV work. It has stopped
working, and nothing flagged it: `health` only checks *feeds*, and NDTV's feed
is live and healthy. The failure is at article-fetch time.

Root cause, isolated by live probe during this analysis — same URL, three
User-Agents:

| Request | Result |
|---|---|
| `curl` default UA | **200**, 6,334 bytes |
| No UA header at all | **200**, 6,334 bytes |
| `extract.UA` (Chrome 126 string) | **403**, 6,098 bytes |

`extract.via_jina()` (`extract.py:148`) sends
`headers={"User-Agent": UA}` — the browser UA needed to fetch publisher pages
directly — to `r.jina.ai` as well. **Jina now rejects browser-like UAs.**

Fix verified end-to-end, live:

| URL | browser UA | no UA |
|---|---|---|
| France 24 wildfires | 403 → 0 chars | **200 → 6,048 chars** |
| NDTV Modi/seafarers | 403 → 0 chars | **200 → 4,895 chars** |

The recovered text is the real article body ("**New Delhi:** Prime Minister
Narendra Modi on Thursday chaired the fourth special meeting of the Cabinet
Committee on Security…").

**Measured downstream cost.** The digest degrades *honestly* — a failed
extraction is labelled `(SUMMARY ONLY)` in the claims prompt and recorded as
`source_kinds: {"summary": N}`, so nothing is fabricated. But claims then rest
on a 400-char (`SUMMARY_CAP`) truncated RSS blurb instead of the article:

| day | fulltext claims | summary claims |
|---|---|---|
| 07-28 | 46 | 0 |
| 07-29 | 72 | 0 |
| 07-30 | 95 | 3 |
| 07-31 | 67 | **7** |

And it visibly thinned the flagship India story. 07-31's India lead,
"Indian Parliament passes strict Anti-Paper Leak Bill", published on **2
outlets** (The Hindu 3 claims, Livemint 5) — the four NDTV articles on exactly
that story all extracted 0 chars.

> Evidence: `debug/2026-07-31/extract/index.json`;
> `debug/2026-07-31/claims.json`; `debug/2026-07-31/llm/2-claims.prompt.txt:243`;
> `extract.py:144-160`; live probes above.

**Fix:** send no `User-Agent` (or a non-browser one) on the `r.jina.ai`
request specifically. Keep `UA` for direct publisher fetches.

*Side note, not a bug:* several France 24 feed links lack the usual
`/<section>/<YYYYMMDD>-` segment (e.g.
`/en/uefa-says-will-boycott-world-cup-…`). I verified these are genuine —
they appear verbatim in `debug/2026-07-31/feeds/france-24.xml`. They 403 like
every other France 24 URL, so they are not a separate problem.

### F4 — `STALE_DAYS` auto-close can never fire on a quiet story · **High**

`STALE_DAYS = 14` is documented as "auto-close after ~14 days with no
development". The logic is inverted.

In `_update_follow`, the quiet path returns at `follow.py:571-575`. The
`_is_closing` check is at `follow.py:584` — **after** the write, reachable only
when `len(dsr["ledger"]) != before`, i.e. only when research *found something*.
`run()` has no separate stale sweep; `_unfollow_closed` only retires follows
whose GitHub issue the owner closed.

Net effect:

- A story that goes genuinely quiet for 14+ days → returns early every day,
  `last_development` never advances, **never closes**.
- A story that is silent for 14 days and *then* produces news → closes, and
  labels that fresh development `kind: "final"`.

It closes on activity and stays open on silence. Combined with F1, follow #3 is
immortal: it can neither update nor close.

> Evidence: `follow.py:409-428`, `follow.py:571-599`, `follow.py:602-634`.

## 4. Medium findings

### F5 — `MAX_ROUNDS` exhaustion reports `complete`

`dossier.py:1496` is `while dsr["rounds"] < MAX_ROUNDS`. When the ceiling is
reached the `while/else` at `dossier.py:1578-1579` sets
`research_state = "complete"` — with no `dbg()` line and no tracer event.

The commit history shows this happening with the frontier wide open: at
`4f7120d` the dossier was `rounds=8, calls=44, state=complete,
open=648`. 648 abandoned questions reported as "complete" is a silent cap.

Note rounds 9 and 10 exceeding `MAX_ROUNDS = 8` is **not** a bug —
`follow.py:565` deliberately raises the ceiling to `rounds + 1` for a
one-round daily delta, and restores it in a `finally`. That part is correct.

### F6 — The follow run clobbers the digest's `extract/index.json`

`digest.yml` runs `digest.py` then `digest.py follow` in the same job against
the same `debug/<date>/`. Both write `extract/index.json`, and the second
overwrites the first:

| day | `funnel.json articles_extracted` | rows surviving in `extract/index.json` |
|---|---|---|
| 07-28 | 25 | 14 |
| 07-29 | 35 | 14 |
| 07-30 | **49** | **4** |
| 07-31 | 45 | 45 (follow made 0 extractions) |

On 07-30 the follow extracted 4 background articles and destroyed the index for
all 49 of the digest's. `report.debug_bundle` reads that file, so
`debug/ANALYSIS.md` now states *"2026-07-30 — Scraping: 4 article(s)"* for a day
that scraped 49. The generated analysis is actively misleading on this row.

07-29's surviving index contains a `vertexaisearch.cloud.google.com`
grounding-redirect URL — a follow artifact — which confirms the mechanism.

Mitigating: the per-article `NNN-*.html` / `.txt` files carry a URL slug in the
name, so they do **not** collide; the raw evidence survives. Only the index is
lost. Fix: name it per run (`extract/index-follow.json`), the pattern
`run-follow.json` / `funnel-follow.json` already uses.

### F7 — The RPD-20 dial fix was never pushed

Local `a040b3d` (now `2b2e02f`), "fix: size the dials to the real RPD 20", is

### F8 — `CLAUDE.md` is wrong: the ceiling *was* learned

`CLAUDE.md` states: *"Note what it did not do on 2026-07-27: that 429 carried no
`quotaId` and no `quotaValue`, so `quota_facts()` returned `""`, nothing was
learned, and `limits.json` was never written."* Commit `2b2e02f`'s message
repeats it.

`followed/_budget/limits.json` exists and is committed:

```json
{"grounded": {"rpd": 20, "model": "gemini-2.5-flash",
              "learned_at": "2026-07-27T23:34:43Z"}}
```

`learned_at` matches commit `c366e6f` (2026-07-27 23:34:43Z) to the second. The
mechanism fired, read 20 off the 429, and has been capping the pool at 18 ever
since. The claim was written locally on 07-28 without the CI commit pulled —
true of the local checkout at the time, false of production. Two documents now
assert something the data contradicts.

Also note `LEARNED_LIMIT_TTL_DAYS = 14`: this value **expires 2026-08-10**,
after which the cap reverts to whatever `MAX_GROUNDED_CALLS_PER_DAY` is in
deployed code — 120 if F7 stays unpushed.

### F9 — The `notable` tier is effectively unpublishable

`weight = distinct_outlets + TIER_WEIGHT[tier] + WIKI_BONUS`, with
`TIER_WEIGHT["notable"] = 0` and `WEIGHT_FLOOR = 5`. A notable story must
therefore clear the floor on outlet count alone — 5 distinct outlets, the same
bar as a major with 3. Over 4 days:

| tier | kept | cut |
|---|---|---|
| lead | 8 | 0 |
| major | 23 | 2 |
| **notable** | **1** | **16** |

Weights separate perfectly at the floor (kept minimum 5, cut maximum 4), so the
floor is the only thing discriminating.

This also defeats the Wikipedia cross-check's stated purpose — *"a curated human
check against volume bias"*. `WIKI_BONUS = 2` cannot promote anything on its
own: a 1-outlet wiki-confirmed story scores 1 + 0 + 2 = 3 < 5. Three
wiki-confirmed stories were cut:

| day | weight | outlets | story |
|---|---|---|---|
| 07-28 | 4 | 2 | Chad to withdraw from the ICC |
| 07-31 | 3 | 1 | Hungary shuts Paks nuclear plant — Danube at record low |
| 07-31 | 3 | 1 | Ebola death toll in DRC passes 1,500 |

The wiki check can currently only reinforce stories that already have volume;
it cannot overrule volume bias, which is what it exists to do.

### F10 — `follow-3.html` is 244 KB, ~60% of it duplicated CSS

For a phone-only app on mobile data:

| page | bytes |
|---|---|
| **follow-3.html** | **249,540** |
| follow-1.html | 23,676 |
| 2026-07-30.html | 101,074 |
| index.html | 71,993 |

`followed/3/dossier.json` accumulates one Google Search-Suggestions blob per
grounded write — 28 of them, ~5.1–6.6 KB each — and `render.py:704` concatenates
all 28 into the page. The page contains **28 `<style>` blocks**, each defining
the same global `.container` / `.chip` / `.carousel` class names, which also
override one another.

`render._suggestions_html` correctly notes the widget must be displayed
unmodified per grounding's Terms of Service, and the markup must stay
byte-for-byte intact. But the ToS requires displaying *the suggestions*, not 28
copies of the same stylesheet. Emitting the most recent blob (or de-duplicating
identical ones) keeps the markup untouched and cuts the page by roughly 60%.
As written this grows ~5 KB per grounded write for the life of the follow.

`anchor.WORD_TARGET = {"lead": 500, "major": 200, "notable": 200}`. Observed

### F15 — Quota day (Pacific) vs digest day (IST) can collide · latent

`Budget` keys on the IST digest date; Google's RPD window resets on Pacific
midnight. `digest.yml`'s three crons (20:30, 22:30, 00:30 UTC) all land on the
same Pacific day and map 1:1 to one IST date, so **the schedule is safe**.

Off-schedule runs are not. `followed/_budget/2026-07-28.json` shows
`daily_quota_exhausted: true` after only **6 of 18** local calls, with a
`"reason": "daily_quota"` deferral. The 07-27 IST day had already spent 18
calls at 17:42–17:56 UTC — the same Pacific day as 07-28's 21:38 UTC cron.
18 + 6 = 24 real requests against RPD 20. The budget file read 6/18 while the
API had been exhausted for a while. Any manual `workflow_dispatch` or local run
reintroduces this.

- **Quota discipline.** Exactly 3 LLM calls per morning, all 4 days.

  counted in `source_kinds`. I specifically checked for claims invented from

- **Checkpointing.** The dossier resumed cleanly across 5 days and 3 runs/day
  without ever restarting.
- **Security posture is clean.** No secret in `data/`, `docs/`, `followed/`,
  `debug/` or `cache/`; no `pull_request_target`; `follow.yml` job-gated on
  `issue.user.login == 'SameerJadav'` + the `follow` label; issue number passed
  via `env:`, never interpolated into `run:`.
- **Stale banner correct.** `docs/index.html` has `id="stale" hidden
  data-digest-date="2026-07-31"` — hidden, because the digest is current.
- **Feeds stable.** 727–734 articles fetched daily, 14/14 live, dedupe working
  (0–2 dupes/day), outlet cap doing real work (73–85 articles trimmed/day).
- **Extraction cache.** 121 URLs, 484 KB — ~4 KB/URL, matching the documented
  ~5 KB estimate.
